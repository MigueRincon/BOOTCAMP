Las tres piezas nuevas

Pieza 1

El middleware (el portero)

Una funcion que revisa si la peticion trae un token valido. Si no lo trae, bloquea el acceso. Si lo trae, deja pasar.

La logica que se ejecuta SOLO cuando el portero deja pasar. Devuelve datos personalizados del usuario.

Contexto

Asi funciona el portero

Antes de escribir codigo, entiende el flujo completo. Cuando el cliente intenta acceder a una ruta privada, esto es lo que pasa paso a paso:

El flujo completo

Cliente
(Postman)
1. Envia una peticion a GET /api/privada/dashboard con el header:
Authorization: Bearer eyJhbGciOiJI...
Middleware
(portero)
2. Revisa: "Hay un header Authorization? Empieza con Bearer?" Si no, responde 401 y aqui se acaba todo.
Middleware
(portero)
3. Extrae el token (lo que viene despues de "Bearer ") y lo verifica con jwt.verify() usando la clave secreta. Si la firma no coincide o el token expiro, responde 401.
MongoDB
4. Con el id que viene dentro del token, busca al usuario en la base de datos para confirmar que sigue existiendo.
Middleware
(portero)
5. Guarda los datos del usuario en req.usuario y llama a next(). "Puedes pasar."
Controlador
(la habitacion)
6. El controlador se ejecuta. Gracias a req.usuario, sabe exactamente quien esta pidiendo los datos. Responde con 200 y la informacion personalizada.

La analogia del hotel, una vez mas

Tu (el huesped)

Eres el cliente (Postman). Llegas a una puerta con tu tarjeta-llave (el token).

La cerradura electronica

Es el middleware. Lee tu tarjeta, verifica si es valida, y decide si abre la puerta o no.

La habitacion

Es el controlador. Solo llegas a ella si la cerradura acepto tu tarjeta. Aqui estan tus cosas (tus datos).

La idea clave del middleware: Se ejecuta ANTES del controlador. Si el token no sirve, el controlador nunca se ejecuta. El middleware corta el flujo y responde con error directamente. El controlador puede asumir tranquilamente que, si llego hasta el, el usuario ya esta verificado.

Que es req.usuario?

Cuando el middleware verifica el token exitosamente, necesita pasarle la informacion del usuario al controlador. Para eso, agrega una propiedad nueva al objeto req (la peticion). Le pone los datos del usuario:

Lo que hace el middleware internamente
// El middleware pone esto en la peticion:
req.usuario = {
  _id: "65a3f...",
  nombre: "Maria",
  email: "maria@email.com",
  rol: "usuario"
};

// Luego llama a next() y el controlador puede usar req.usuario

Es como si el portero te pegara una calcomanía en la mano que dice tu nombre. Cualquier persona adentro del hotel puede verla y saber quién eres sin volver a pedirte la cédula.

Preparacion

2Obtener un token

Para probar rutas privadas necesitas un token. Vas a hacer login ahora y guardar ese token en Postman para usarlo despues.

Paso 1: Haz login

Envia un POST a /api/auth/login con las credenciales del usuario que registraste:

Body (raw JSON)
{
  "email": "estudiante@test.com",
  "password": "clave123"
}

Paso 2: Copia el token

En la respuesta vas a ver algo como esto:

Respuesta del login
{
  "exitoso": true,
  "mensaje": "Login exitoso",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6IjY4M...",
  "usuario": {
    "id": "683f1a2b...",
    "nombre": "Estudiante Test",
    "email": "estudiante@test.com",
    "rol": "usuario"
  }
}

Selecciona y copia todo el valor del campo "token" (sin las comillas). Ese texto largo que empieza con eyJ es tu token JWT. Lo vas a necesitar en las pruebas.

Consejo de Postman: Puedes pegar el token en una variable de entorno de Postman para no tener que copiarlo cada vez. Pero por ahora, con copiarlo al portapapeles y pegarlo cuando lo necesites es suficiente.

Paso 3 (opcional): Miralo por dentro

Entra a jwt.io y pega tu token. Vas a ver las tres partes:

  • Header: El algoritmo (HS256).
  • Payload: Tu id, tu rol, cuando se creo (iat) y cuando expira (exp).
  • Signature: La firma que garantiza que nadie lo modifico.

El id que ves en el payload es el _id de tu usuario en MongoDB. Ese es el dato que el middleware va a usar para saber quien eres.

Recuerda: El token tiene fecha de expiracion (JWT_EXPIRES_IN=1d en tu .env). Si han pasado mas de 24 horas desde que lo generaste, ya no servira. Tendras que hacer login de nuevo para obtener uno fresco.

Construccion

3Crear el middleware

Esta es la pieza mas importante del ejercicio. El middleware es la funcion que se pone "en medio" entre la peticion y el controlador. Es el portero del hotel.

Paso 1: Crear la carpeta y el archivo

En la raiz de tu proyecto, crea una carpeta middleware (si no existe) y dentro un archivo auth.js:

Terminal
mkdir middleware
touch middleware/auth.js

Paso 2: Escribir el middleware

Abre middleware/auth.js y escribe este codigo completo. Lee cada comentario, cada uno explica una decision:

middleware/auth.js
const jwt = require('jsonwebtoken');
const User = require('../models/User');

const proteger = async (req, res, next) => {
  try {
    let token;

    // PASO 1: Buscar el token en el header Authorization
    // El cliente lo envia asi: "Bearer eyJhbGciOiJI..."
    // Necesitamos extraer solo la parte del token (sin "Bearer ")
    if (
      req.headers.authorization &&
      req.headers.authorization.startsWith('Bearer')
    ) {
      // split(' ') separa "Bearer eyJhbG..." en ["Bearer", "eyJhbG..."]
      // [1] toma la segunda parte: el token puro
      token = req.headers.authorization.split(' ')[1];
    }

    // PASO 2: Si no hay token, rechazar inmediatamente
    if (!token) {
      return res.status(401).json({
        exitoso: false,
        mensaje: 'No autorizado, no hay token'
      });
    }

    // PASO 3: Verificar que el token sea valido
    // jwt.verify() hace dos cosas:
    //   - Verifica que la firma coincida (que nadie lo modifico)
    //   - Verifica que no haya expirado
    // Si algo falla, LANZA UN ERROR y caemos al catch
    const decodificado = jwt.verify(token, process.env.JWT_SECRET);

    // PASO 4: Buscar al usuario en la base de datos
    // El token tiene el id del usuario en su payload
    // Lo buscamos para confirmar que sigue existiendo
    const usuario = await User.findById(decodificado.id);

    if (!usuario) {
      return res.status(401).json({
        exitoso: false,
        mensaje: 'El usuario de este token ya no existe'
      });
    }

    // PASO 5: Adjuntar el usuario a la peticion
    // Esto es lo que permite que el controlador sepa QUIEN esta pidiendo
    req.usuario = usuario;

    // PASO 6: Dejar pasar al siguiente paso (el controlador)
    next();

  } catch (error) {
    // Si jwt.verify() fallo (firma invalida o token expirado),
    // caemos aqui
    return res.status(401).json({
      exitoso: false,
      mensaje: 'Token invalido o expirado'
    });
  }
};

module.exports = { proteger };

Entendiendo cada paso

PasoQue haceSi falla
1Busca el header Authorization y extrae el tokenEl token queda como undefined
2Verifica que el token existaResponde 401: "no hay token"
3jwt.verify() valida la firma y la expiracionLanza error → catch → 401
4Busca al usuario en MongoDB con el id del payloadResponde 401: "usuario no existe"
5Guarda al usuario en req.usuario-
6Llama a next() para pasar al controlador-

Fijate en el patron: El middleware tiene MULTIPLES puntos de salida donde puede rechazar la peticion (3 return con 401). Solo si TODOS los chequeos pasan, llega al next(). Esto es seguridad por capas: cada paso es un filtro mas.

Pregunta para pensar: Por que buscamos al usuario en la base de datos (paso 4) si el token ya tiene el id? Porque el usuario pudo haber sido eliminado DESPUES de que se genero el token. El token sigue siendo "valido" tecnicamente, pero el usuario ya no existe. Siempre hay que verificar contra la fuente de verdad: la base de datos.

4Crear la ruta privada

Ahora creamos la "puerta con cerradura". Una ruta que usa el middleware como guardaespaldas: solo deja pasar si el token es valido.

Paso 1: Crear el archivo de rutas

Crea un nuevo archivo en tu carpeta routes/:

Terminal
touch routes/privadaRoutes.js

Paso 2: Escribir las rutas

routes/privadaRoutes.js
const express = require('express');
const router = express.Router();

// Importar el middleware (el portero)
const { proteger } = require('../middleware/auth');

// Importar el controlador
const { dashboard, miPerfil } = require('../controllers/privadaController');

// RUTA 1: Dashboard privado
// Lee esta linea de izquierda a derecha:
//   GET '/dashboard' --> primero pasa por 'proteger' --> si pasa, ejecuta 'dashboard'
router.get('/dashboard', proteger, dashboard);

// RUTA 2: Mi perfil
// Misma logica: el middleware protege, el controlador responde
router.get('/mi-perfil', proteger, miPerfil);

module.exports = router;

La magia esta en el orden

Mira esta linea con atencion:

Asi se lee
router.get('/dashboard', proteger, dashboard);
//                        ^^^^^^^^  ^^^^^^^^^
//                        PRIMERO   DESPUES
//                        (portero) (controlador)

Express ejecuta las funciones en el orden en que las pones. Primero corre proteger (el middleware). Si proteger llama a next(), entonces corre dashboard (el controlador). Si proteger responde con un error (401), dashboard nunca se ejecuta.

Peticion
GET /dashboard
→ Llega la peticion al servidor
proteger
→ Token valido? SI → llama a next()
Token invalido? NO → responde 401 y se acaba aqui
dashboard
→ Solo se ejecuta si el middleware dejo pasar. Usa req.usuario para saber quien es.

Compara con una ruta SIN proteccion:
router.get('/productos', obtenerProductos); ← no tiene middleware, cualquiera entra
router.get('/dashboard', proteger, dashboard); ← tiene middleware, solo entran con token

Construccion

5Crear el controlador privado

El controlador es la "habitacion del hotel". Es la logica que se ejecuta solo cuando el portero ya verifico que tienes un token valido. Aqui usamos req.usuario para responder con datos personalizados.

Paso 1: Crear el archivo

Terminal
touch controllers/privadaController.js

Paso 2: Escribir los controladores

controllers/privadaController.js
// =====================================================
// CONTROLADORES PRIVADOS
// Estas funciones SOLO se ejecutan si el middleware
// 'proteger' verifico el token exitosamente.
// En todas ellas, req.usuario ya existe y contiene
// los datos del usuario logueado.
// =====================================================

// GET /api/privada/dashboard
const dashboard = async (req, res) => {
  try {
    // req.usuario fue puesto por el middleware 'proteger'
    // Contiene los datos del usuario que hizo login

    res.status(200).json({
      exitoso: true,
      mensaje: `Bienvenido al dashboard, ${req.usuario.nombre}`,
      datos: {
        usuario: {
          id: req.usuario._id,
          nombre: req.usuario.nombre,
          email: req.usuario.email,
          rol: req.usuario.rol
        },
        info: 'Esta informacion solo la ves porque tienes un token valido',
        timestamp: new Date().toLocaleString('es-CO', {
          timeZone: 'America/Bogota'
        })
      }
    });
  } catch (error) {
    res.status(500).json({
      exitoso: false,
      mensaje: 'Error en el dashboard',
      error: error.message
    });
  }
};

// GET /api/privada/mi-perfil
const miPerfil = async (req, res) => {
  try {
    // Aqui podriamos hacer consultas adicionales a MongoDB
    // usando req.usuario._id para traer datos relacionados
    // Por ahora devolvemos el perfil basico

    res.status(200).json({
      exitoso: true,
      perfil: {
        id: req.usuario._id,
        nombre: req.usuario.nombre,
        email: req.usuario.email,
        rol: req.usuario.rol,
        creadoEn: req.usuario.createdAt
      }
    });
  } catch (error) {
    res.status(500).json({
      exitoso: false,
      mensaje: 'Error al obtener perfil',
      error: error.message
    });
  }
};

module.exports = { dashboard, miPerfil };

Lo importante: req.usuario

Fijate que en ningun momento el controlador verifica el token. No importa ni necesita hacerlo. Eso ya lo hizo el middleware. El controlador simplemente usa req.usuario confiando en que si llego hasta aqui, el usuario es real y esta verificado.

Middleware

Se encarga de la seguridad

Verifica el token, busca al usuario, rechaza si algo falla. Separacion de responsabilidades.

Controlador

Se encarga de la logica

Usa req.usuario para devolver datos personalizados. No sabe nada de tokens.

Esto es un patron profesional: separar la autenticacion de la logica de negocio. En empresas reales, el middleware de auth se escribe UNA VEZ y se reutiliza en decenas o cientos de rutas. Cada controlador se enfoca solo en su trabajo.

Prueba 1 de 4

Sin token: acceso denegado

La primera prueba es la mas basica: intentar entrar a una ruta protegida sin enviar ningun token. El portero deberia rechazarte inmediatamente.

Que hacer en Postman

GET http://localhost:3000/api/privada/dashboard Send
Params
Authorization
Headers
Body
No envies ningun header Authorization. Dejalo vacio.

Simplemente crea un GET a http://localhost:3000/api/privada/dashboard y dale Send sin agregar nada mas. Sin headers especiales, sin body, nada.

Que deberias recibir

Respuesta esperada (Status: 401 Unauthorized)
{
  "exitoso": false,
  "mensaje": "No autorizado, no hay token"
}

Por que funciona asi

Cuando no envias el header Authorization, el middleware cae en el paso 2:

middleware/auth.js - Lo que se ejecuto
// El header Authorization no existe, asi que token queda undefined
if (!token) {
  return res.status(401).json({
    exitoso: false,
    mensaje: 'No autorizado, no hay token'
  });
}
// next() NUNCA se llama. El controlador NUNCA se ejecuta.

Esto es exactamente lo que queremos. El middleware bloqueo la peticion. El controlador dashboard nunca llego a ejecutarse. El portero hizo su trabajo: "No tienes tarjeta-llave? No entras."

Prueba 2 de 4

Token inventado: acceso denegado

Ahora vamos a intentar algo mas astuto: enviar un token, pero uno falso. Inventado. Basura. A ver si el portero se deja enganar.

Que hacer en Postman

Crea un GET a http://localhost:3000/api/privada/dashboard, pero esta vez agrega un header Authorization con un token falso:

GET http://localhost:3000/api/privada/dashboard Send
Params
Authorization
Headers
Body
Type: Bearer Token • Token: estoEsUnTokenFalsoInventado123

Como agregarlo en Postman (paso a paso)

  1. Ve a la pestana Authorization de la peticion
  2. En el dropdown Type, selecciona Bearer Token
  3. En el campo Token, escribe cualquier cosa: estoEsUnTokenFalsoInventado123
  4. Dale Send

Alternativa sin la pestana Authorization: Tambien puedes ir a la pestana Headers y agregar manualmente:
Key: Authorization
Value: Bearer estoEsUnTokenFalsoInventado123
Ambas formas hacen lo mismo. Postman agrega el header por ti cuando usas la pestana Authorization.

Que deberias recibir

Respuesta esperada (Status: 401 Unauthorized)
{
  "exitoso": false,
  "mensaje": "Token invalido o expirado"
}

Por que funciona asi

Esta vez el middleware llego mas lejos. Paso los pasos 1 y 2 (si encontro un token). Pero cayo en el paso 3:

middleware/auth.js - Lo que se ejecuto
// jwt.verify() intenta verificar el token falso
// La firma NO coincide con la clave secreta del servidor
// LANZA UN ERROR
const decodificado = jwt.verify(token, process.env.JWT_SECRET);
// ^^^ Error! La firma no es valida

// Caemos al catch:
catch (error) {
  return res.status(401).json({
    exitoso: false,
    mensaje: 'Token invalido o expirado'
  });
}

Esto es la magia de JWT: Un atacante puede inventar cualquier token que quiera, pero sin la clave secreta (JWT_SECRET) no puede generar una firma valida. jwt.verify() detecta inmediatamente que la firma no coincide y lo rechaza. Es matematicamente imposible falsificar un token sin la clave.

Prueba 4 de 4

Token expirado: acceso denegado

La ultima prueba: que pasa cuando un token es real pero ya se le vencio el tiempo. Recordaras que en el .env pusimos JWT_EXPIRES_IN=1d (1 dia). Vamos a simular un token expirado.

El problema: no vamos a esperar 24 horas

Obviamente no vamos a sentarnos a esperar un dia entero. En lugar de eso, vamos a hacer un truco temporal para generar un token que expire rapidamente.

Paso 1: Cambia la expiracion temporalmente

En tu .env, cambia la linea de expiracion a 10 segundos:

.env (cambio temporal)
JWT_EXPIRES_IN=10s

Importante: Esto es TEMPORAL, solo para esta prueba. Al terminar lo vuelves a poner en 1d. Si usas nodemon, el servidor se reinicia automaticamente al guardar el .env. Si no, reinicialo manualmente.

Paso 2: Haz login para obtener un token de 10 segundos

POST /api/auth/login (Body raw JSON)
{
  "email": "estudiante@test.com",
  "password": "clave123"
}

Copia el token. Este token expira en 10 segundos.

Paso 3: Espera 15 segundos y luego usa el token

Espera al menos 15 segundos (para estar seguro) y luego envia el GET a /api/privada/dashboard con ese token.

Que deberias recibir

Respuesta esperada (Status: 401 Unauthorized)
{
  "exitoso": false,
  "mensaje": "Token invalido o expirado"
}

Que paso

jwt.verify() reviso el campo exp (expiration) del token y encontro que la fecha ya paso. Lanzo un error de tipo TokenExpiredError y caimos al catch del middleware.

Por que esto importa en la vida real: Si alguien roba un token (por ejemplo, interceptando la red), ese token no le sirve para siempre. Tiene fecha de vencimiento. Por eso en produccion se usan tokens de corta duracion (15 minutos, 1 hora) con refresh tokens para renovarlos automaticamente.

Paso 4: Restaurar la expiracion

NO olvides este paso. Vuelve a poner la expiracion en 1 dia en tu .env:

.env (restaurar)
JWT_EXPIRES_IN=1d

Proteger tus rutas CRUD

Ya sabes como funciona el middleware. Ahora el reto: aplica la proteccion a las rutas CRUD de usuarios (o productos) que ya tenias de clases anteriores.

El reto

Abre tu archivo routes/userRoutes.js (o el equivalente de tu proyecto). Ahora mismo, todas las rutas estan abiertas. Tu mision es decidir cuales proteger.

Reto

Protege tus rutas con criterio

Meta: No todas las rutas necesitan proteccion. Piensa cual deberia ser publica y cual privada.

Esta es una decision que tomaras constantemente en tu vida profesional. Usa esta guia:

RutaProteger?Por que
GET /api/usersDependeVer listado puede ser publico (catalogo) o privado (panel admin)
GET /api/users/:idRecomendadoDatos de un usuario especifico suelen ser privados
POST /api/usersSiCrear registros deberia requerir estar logueado
PUT /api/users/:idSiModificar datos es una accion que necesita verificacion
DELETE /api/users/:idSiBorrar es la accion mas peligrosa, siempre protegida

Como hacerlo

Ya sabes el patron. Solo tienes que importar el middleware y agregarlo antes del controlador:

routes/userRoutes.js (ejemplo)
const express = require('express');
const router = express.Router();
const {
  obtenerUsuarios,
  obtenerUsuarioPorId,
  crearUsuario,
  actualizarUsuario,
  eliminarUsuario
} = require('../controllers/userController');

// Importar el middleware
const { proteger } = require('../middleware/auth');

// PUBLICA: ver listado
router.get('/', obtenerUsuarios);

// PROTEGIDAS: requieren token
router.get('/:id', proteger, obtenerUsuarioPorId);
router.post('/', proteger, crearUsuario);
router.put('/:id', proteger, actualizarUsuario);
router.delete('/:id', proteger, eliminarUsuario);

module.exports = router;

Prueba cada ruta

Una vez que protejas las rutas, prueba cada una en Postman dos veces:

  1. Sin token: Deberia devolver 401. Si lo hace, la proteccion funciona.
  2. Con token: Deberia funcionar normalmente. Si lo hace, no rompiste nada.

Regla de oro para proteger rutas: Si la ruta lee datos sensibles, los modifica, o los borra → protegela. Si la ruta muestra informacion publica que cualquier visitante deberia ver (como un catalogo de productos) → dejala abierta. En la duda, protege. Siempre es mas facil abrir una puerta que ya tenia cerradura que ponerle cerradura a una puerta que ya estaba abierta.

Conceptos clave que aprendiste

  • Middleware: Una funcion que se ejecuta ENTRE la peticion y el controlador. Puede dejar pasar (next()) o bloquear (responder con error).
  • Bearer Token: El formato estandar para enviar JWT: Authorization: Bearer <token>
  • jwt.verify(): La funcion que valida la firma y la expiracion. Si algo falla, lanza error.
  • req.usuario: La forma de pasar informacion del middleware al controlador. El middleware lo escribe, el controlador lo lee.
  • 401 vs 403: 401 = "no se quien eres" (autenticacion). 403 = "se quien eres pero no puedes" (autorizacion).
