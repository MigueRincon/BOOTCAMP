Módulo 1 · Fundamentos

Introducción a la autenticación

Tenemos una API en Node + Express que se conecta a MongoDB. Funciona: podemos crear, leer, actualizar y borrar datos. Pero hay un problema enorme que todavía no hemos resuelto.

El problema

Ahora mismo, cualquier persona en el mundo que conozca la URL de nuestra API puede:

  • Ver todos los usuarios con GET /api/users
  • Borrar cualquier producto con DELETE /api/products/:id
  • Modificar datos que no le pertenecen
  • Crear miles de registros basura

No hay ninguna puerta, ningún candado, ningún portero. Es como tener una casa sin cerraduras donde cualquiera entra, toca tus cosas y se va.

Esto es exactamente lo que NO queremos en producción. Una API sin autenticación es una API insegura, y ninguna empresa la pondría en internet con datos reales.

¿Qué vamos a aprender hoy?

Al final de esta clase vas a entender y haber construido un sistema completo donde:

  • Un usuario se registra con email y contraseña
  • La contraseña se guarda cifrada (nunca en texto plano)
  • El usuario hace login y recibe un token
  • Ese token le sirve de "pase" para acceder a rutas protegidas
  • Las rutas privadas rechazan a quien no tenga un token válido

Una analogía para todo el curso

Vamos a usar la analogía de un hotel durante toda la clase, porque encaja perfecto:

🛎️ Recepción (Login)

Muestras tu identificación. Si eres quien dices ser, te dan una tarjeta-llave.

🎫 Tarjeta-llave (Token)

No es tu identificación. Es un pase temporal que abre ciertas puertas.

🚪 Puertas (Rutas protegidas)

Cada puerta verifica tu tarjeta antes de abrirse. Sin tarjeta válida, no entras.

Ten esta imagen en mente. Cuando lleguemos al código, vas a reconocer cada pieza.

📌 Importante: No vamos a instalar nada todavía ni a escribir código en esta primera parte. Primero entendemos los conceptos. El código viene después, y cuando llegue, ya sabrás por qué hacemos cada cosa.

Módulo 2 · Fundamentos

Autenticación vs Autorización

Dos palabras que se parecen, se confunden todo el tiempo, y significan cosas muy distintas. Si entiendes la diferencia, ya tienes media batalla ganada.

Definiciones simples

ConceptoPregunta que respondeEjemplo en el hotel
Autenticación
(Authentication / Authn)		¿Quién eres?Muestras tu cédula en recepción para probar tu identidad.
Autorización
(Authorization / Authz)		¿Qué puedes hacer?Tu tarjeta abre tu habitación, pero NO el cuarto de mantenimiento ni la suite presidencial.

La regla de oro

Primero autenticas, luego autorizas. No puedes saber qué puede hacer alguien (autorización) si primero no sabes quién es (autenticación). El orden siempre es ese.

Ejemplo concreto en nuestra API

Imagina que tenemos usuarios con dos roles: usuario y admin.

Autenticación

María hace login con su email y contraseña. El sistema confirma: "Sí, eres María". Eso es autenticación. Ya sabemos quién es.

Autorización

Ahora María intenta borrar un producto: DELETE /api/products/123. El sistema revisa: "María es rol usuario, no admin. Borrar productos requiere ser admin. Permiso denegado." Eso es autorización.

María
1. "Soy María, esta es mi contraseña" → Autenticación
API
2. "Confirmado, eres María. Toma tu token."
María
3. "Quiero borrar este producto" → Autorización
API
4. "Eres María, pero NO eres admin. ❌ Denegado."

💡 Truco para recordar: AuthN = "who you are" (iNdentidad). AuthZ = "what you can do" (autoriZación de acciones).

En esta clase

Nos vamos a enfocar principalmente en autenticación (probar quién eres) porque es el fundamento. Tocaremos autorización al final con un ejemplo de roles, pero lo importante hoy es: registro, login, tokens y proteger rutas.

Módulo 3 · Fundamentos

¿Por qué necesitamos autenticar APIs?

Antes de aprender el "cómo", entendamos bien el "por qué". Una API es una puerta a tus datos, y las puertas necesitan control.

El problema del estado en HTTP

HTTP es un protocolo sin estado (stateless). Esto significa algo crucial:

El servidor NO recuerda peticiones anteriores. Cada petición que llega es como si fuera la primera vez que ve a ese cliente. No tiene memoria de que "este usuario ya se identificó hace 2 minutos".

Esto genera un reto: si el servidor no recuerda nada, ¿cómo sabe en la petición #2 que eres el mismo que se autenticó en la petición #1? La respuesta es: el cliente debe probar su identidad en cada petición, normalmente enviando un token.

Qué protege la autenticación

🔒 Datos privados

Que solo tú veas tu información: tu perfil, tus pedidos, tus mensajes.

🛡️ Acciones peligrosas

Que no cualquiera borre, modifique o cree registros sin permiso.

📊 Identidad para el negocio

Saber quién hace qué: auditoría, historial, personalización.

⚖️ Cumplimiento legal

Leyes de protección de datos (GDPR, Habeas Data en Colombia) exigen controlar el acceso.

Rutas públicas vs privadas

No todo necesita autenticación. Una API típica mezcla ambas:

TipoEjemplo¿Necesita token?
PúblicaPOST /api/auth/registerNo (todavía no tienes cuenta)
PúblicaPOST /api/auth/loginNo (es donde obtienes el token)
PúblicaGET /api/productsOpcional (ver catálogo)
PrivadaGET /api/users/meSí (tu perfil)
PrivadaPOST /api/productsSí (crear producto)
PrivadaDELETE /api/products/:idSí (acción destructiva)

💡 Pregunta de clase: ¿Por qué /login y /register NO pueden requerir token? Piénsalo: si necesitaras un token para hacer login... ¿de dónde sacarías el token antes de tener cuenta? Es un huevo y la gallina. Esas rutas tienen que ser públicas.

Módulo 4 · Fundamentos

Tipos de autenticación para APIs

No existe un solo método. Cada uno tiene ventajas, desventajas y un escenario donde brilla. Vamos del más simple al más sofisticado.

Panorama general

Simple

Basic Auth

Usuario y contraseña codificados en cada petición. Fácil pero limitado.

Simple

API Keys

Una clave secreta que identifica a la aplicación. Común entre servicios.

Intermedio

Session-based

El servidor crea una sesión y guarda un ID en una cookie.

Intermedio

Token-based (JWT)

El cliente guarda un token firmado. El estándar moderno para APIs.

Avanzado

OAuth 2.0

"Iniciar sesión con Google". Delegas la autenticación a un tercero.

Avanzado

OpenID Connect

Capa de identidad sobre OAuth 2.0. Lo que usan las grandes empresas.

1. Basic Authentication

El cliente envía usuario:contraseña codificado en Base64 en el header de cada petición.

Header de la petición
Authorization: Basic bWFyaWE6bWlDb250cmFzZW5hMTIz

Problema grave: Base64 NO es cifrado, es solo codificación. Cualquiera puede decodificarlo. Solo es seguro sobre HTTPS, y aún así envías la contraseña en cada petición. Casi nadie lo usa hoy para apps reales.

2. API Keys

Una cadena larga y secreta que identifica a quien hace la petición. Muy usada para comunicación entre servidores o para APIs públicas con límites de uso.

Header de la petición
x-api-key: sk_live_4eC39HqLyjWDarjtT1zdp7dc

Identifica a la aplicación, no necesariamente a un usuario. Piensa en la API de OpenAI o Stripe: te dan una API key.

3. Session-based (sesiones con cookies)

El enfoque clásico de las páginas web tradicionales:

  1. Haces login.
  2. El servidor crea una "sesión" y la guarda en su memoria o base de datos.
  3. Te devuelve un sessionId en una cookie.
  4. El navegador envía esa cookie automáticamente en cada petición.
  5. El servidor busca el sessionId en su almacén y sabe quién eres.

Característica clave: el estado vive en el servidor. Esto se llama ser stateful.

4. Token-based con JWT

El enfoque moderno para APIs, y el que vamos a implementar hoy:

  1. Haces login.
  2. El servidor genera un token firmado (un JWT) con tu información dentro.
  3. Te devuelve el token. El servidor no guarda nada.
  4. El cliente guarda el token y lo envía en cada petición.
  5. El servidor verifica la firma del token y sabe quién eres, sin consultar ninguna base de datos de sesiones.

Característica clave: el servidor no guarda estado. Esto se llama ser stateless. Por eso JWT escala tan bien.

Comparación: Sesiones vs JWT

Sesiones (stateful)JWT (stateless)
¿Dónde vive el estado?En el servidorEn el cliente (el token)
EscalabilidadMás difícil (hay que compartir sesiones entre servidores)Fácil (cualquier servidor verifica el token)
Cerrar sesiónInmediato (borras la sesión)Más complejo (el token sigue válido hasta expirar)
Ideal paraWebs tradicionales con servidorAPIs, móviles, microservicios

5. OAuth 2.0 y OpenID Connect

Es lo que pasa cuando ves "Iniciar sesión con Google / GitHub / Facebook". En vez de manejar tú las contraseñas, le delegas la autenticación a un proveedor confiable. Google confirma quién eres y te da un token. Es potente pero más complejo, y lo veremos a fondo en la sección de "Otras opciones".

✅ Decisión para esta clase: Vamos a implementar autenticación basada en JWT, porque es el estándar para APIs modernas, encaja perfecto con Node/Express/MongoDB, y entenderlo te da la base para todo lo demás.

Módulo 5 · Cómo funciona

¿Qué hace el frontend y qué hace el backend?

La autenticación es un trabajo de equipo entre dos partes. Confundir quién hace qué es la causa #1 de errores de seguridad en estudiantes (y en profesionales).

Reparto de responsabilidades

Tarea¿Quién?Detalle
Mostrar formulario de loginFrontendInputs de email y contraseña
Enviar credencialesFrontendPOST a /api/auth/login
Verificar credencialesBackendComparar contra la base de datos
Cifrar/comparar contraseñaBackendCon bcrypt. NUNCA en el frontend.
Generar el tokenBackendFirmar el JWT con la clave secreta
Guardar el tokenFrontendEn memoria, localStorage o cookie
Enviar token en cada peticiónFrontendEn el header Authorization
Verificar el tokenBackendEn el middleware, antes de la ruta
Decidir qué puede hacerBackendAutorización por roles

⚠️ Regla absoluta de seguridad: El frontend NUNCA decide si tienes permiso. El frontend solo pide y muestra. La verificación SIEMPRE ocurre en el backend. ¿Por qué? Porque el frontend corre en el navegador del usuario, y el usuario puede modificarlo. Nunca confíes en el cliente.

El frontend "miente bien", el backend "no confía"

Una forma de entenderlo:

  • El frontend puede ocultar el botón de "Borrar" si no eres admin. Pero eso es solo cosmética, para que la interfaz se vea bien.
  • El backend igual debe rechazar el DELETE aunque el botón esté oculto. Porque un usuario malicioso puede llamar a la API directamente con Postman, saltándose tu interfaz por completo.

📌 Frase para recordar: "La seguridad del frontend es una sugerencia. La seguridad del backend es la ley."

¿Dónde guarda el frontend el token?

LugarVentajaRiesgo
Memoria (variable JS)Más seguro contra roboSe pierde al recargar la página
localStoragePersiste, fácil de usarVulnerable a ataques XSS
Cookie httpOnlyJavaScript no puede leerla (protege de XSS)Vulnerable a CSRF si no se configura bien

Para empezar a aprender, usaremos el header Authorization y dejaremos que el cliente (Postman al inicio) maneje el token. La decisión de dónde guardarlo en una app real depende del contexto.

Módulo 6 · Cómo funciona

Anatomía de un token JWT

JWT significa JSON Web Token. Es el corazón de nuestra autenticación. Vamos a abrirlo y ver exactamente qué tiene dentro.

Cómo se ve un JWT

Un JWT es una cadena larga de texto dividida en tres partes separadas por puntos:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6IjY1YTNmIiwibm9tYnJlIjoiTWFyaWEiLCJyb2wiOiJ1c3VhcmlvIn0.dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
Header (rojo) Payload (morado) Signature (azul)
HEADER
Dice qué algoritmo se usó para firmar y que es de tipo JWT.
PAYLOAD
Los datos (claims): id del usuario, nombre, rol, fecha de expiración.
SIGNATURE
La firma que garantiza que nadie modificó el token.

Parte 1: El Header

Si decodificamos la primera parte (es Base64, no cifrado), obtenemos:

Header decodificado
{
  "alg": "HS256",
  "typ": "JWT"
}

alg es el algoritmo de firma (HS256 es muy común). typ es el tipo de token.

Parte 2: El Payload

Aquí van los datos que queremos transportar. Cada dato se llama un claim:

Payload decodificado
{
  "id": "65a3f...",
  "nombre": "Maria",
  "rol": "usuario",
  "iat": 1705320000,
  "exp": 1705406400
}

Algunos claims son estándar:

  • iat (issued at): cuándo se creó el token.
  • exp (expiration): cuándo expira. ¡Muy importante para seguridad!
  • sub (subject): a quién pertenece el token.

⚠️ ENORME advertencia de seguridad: El payload NO está cifrado, solo codificado en Base64. Cualquiera puede leerlo. NUNCA pongas contraseñas, números de tarjeta o datos sensibles en el payload. Pon solo lo necesario: id, rol, quizá el nombre.

Parte 3: La Signature (la magia)

Esta es la parte que hace que un JWT sea confiable. Se calcula así:

Cómo se genera la firma (concepto)
firma = HMAC_SHA256(
  base64(header) + "." + base64(payload),
  CLAVE_SECRETA   // ← solo el servidor la conoce
)

La firma se genera usando el header, el payload y una clave secreta que solo el servidor conoce.

¿Por qué esto es seguro?

Imagina que un atacante intercepta tu token y cambia el payload de "rol": "usuario" a "rol": "admin". ¿Qué pasa?

  1. El atacante puede cambiar el payload fácilmente (es solo Base64).
  2. PERO la firma ya no coincidirá, porque la firma se calculó con el payload original.
  3. Para recalcular la firma correcta, necesitaría la clave secreta... que no tiene.
  4. Cuando el servidor recibe el token, recalcula la firma. No coincide → token rechazado.

✅ La idea clave: No importa que cualquiera pueda LEER el token. Lo que importa es que nadie puede MODIFICARLO sin la clave secreta. La firma es un sello a prueba de manipulación.

💡 Para explorar en clase: Entra a jwt.io, pega un token y míralo desarmado en sus tres partes. Es la mejor forma de que los estudiantes "vean" lo que estamos explicando.

Módulo 7 · Cómo funciona

Diagramas de flujo completos

Ahora juntamos todo lo aprendido en tres diagramas: registro, login y acceso a una ruta protegida. Estos diagramas son el mapa de lo que vamos a programar.

Flujo 1: Registro (Sign Up)

Cliente
1. POST /api/auth/register
Envía: { nombre, email, contraseña }
Backend
2. ¿El email ya existe? Si sí → error. Si no, continúa.
Backend
3. Cifra la contraseña con bcrypt (hash + salt).
MongoDB
4. Guarda el usuario con la contraseña YA cifrada.
Backend
5. Responde 201: "Usuario creado". (Sin devolver la contraseña.)

Flujo 2: Login (Sign In)

Cliente
1. POST /api/auth/login
Envía: { email, contraseña }
MongoDB
2. Backend busca el usuario por email.
Backend
3. Compara la contraseña enviada con el hash guardado (bcrypt.compare).
Backend
4. ¿Coincide? Si no → 401 "Credenciales inválidas". Si sí, continúa.
Backend
5. Genera un JWT firmado con { id, rol } y la clave secreta.
Cliente
6. Recibe el token y lo guarda. ¡Ya está autenticado!

Flujo 3: Acceder a una ruta protegida

Cliente
1. GET /api/users/me
Header: Authorization: Bearer <token>
Middleware
2. Extrae el token del header. ¿Existe? Si no → 401.
Middleware
3. Verifica la firma con la clave secreta. ¿Válida y no expirada? Si no → 401.
Middleware
4. Extrae el id del payload y lo pone en req.usuario. Llama a next().
Controlador
5. Ahora sabe quién es. Busca y devuelve los datos del usuario.

📌 Fíjate en el patrón: El middleware es el "portero". Se ejecuta ANTES del controlador. Si el token no sirve, ni siquiera llegamos al controlador. Esa separación es elegante: el controlador asume que, si llegó hasta él, el usuario ya está verificado.

Módulo 8 · Cómo funciona

¿Qué hacen las empresas en el mundo real?

Lo que vamos a construir hoy es la base. Pero es bueno saber hacia dónde escala esto cuando trabajas en una empresa grande.

El espectro de la complejidad

EtapaQué usanEjemplo
Proyecto pequeño / MVPJWT propio (lo de hoy)Un startup validando una idea
Producto en crecimientoJWT + refresh tokens + rolesUna app con miles de usuarios
Empresa medianaOAuth 2.0 + OpenID Connect"Login con Google" integrado
Empresa grandeProveedores de identidad gestionadosAuth0, Okta, AWS Cognito, Firebase Auth

Proveedores de identidad (Identity Providers)

Las empresas grandes rara vez programan su propia autenticación desde cero. ¿Por qué? Porque la seguridad es difícil y un error cuesta carísimo. En lugar de eso, usan servicios especializados:

Auth0 / Okta

Plataformas completas de identidad. Login social, MFA, gestión de usuarios, todo gestionado.

AWS Cognito

El servicio de identidad de Amazon. Se integra con el ecosistema AWS.

Firebase Auth

De Google. Muy popular en apps móviles y proyectos pequeños/medianos.

Keycloak

Open source y autohospedado. Para empresas que quieren control total.

Técnicas que añaden las empresas serias

1. Refresh Tokens

Un problema de JWT: si el token dura mucho y lo roban, el atacante tiene acceso por mucho tiempo. La solución: tokens de acceso cortos (15 minutos) más un refresh token de larga duración que sirve solo para pedir nuevos tokens de acceso. Lo vemos en la sección 16.

2. MFA (Autenticación Multifactor)

Algo que sabes (contraseña) + algo que tienes (código en tu celular) + algo que eres (huella). Las empresas lo exigen cada vez más. El típico "código de 6 dígitos" es MFA.

3. Rate limiting

Limitar cuántos intentos de login puede hacer alguien. Bloquea ataques de fuerza bruta donde un bot prueba miles de contraseñas.

4. Rotación de claves secretas

Cambiar la clave que firma los tokens periódicamente, para que un secreto filtrado no sirva para siempre.

📌 Mensaje para los estudiantes: No se asusten con esta lista. Empezamos por lo fundamental: JWT propio. Una vez entiendes el concepto base, todas estas técnicas son variaciones del mismo principio. Caminamos antes de correr.

Módulo 10 · Implementación

1Hashing de contraseñas

La regla #1 de seguridad: NUNCA guardes contraseñas en texto plano. Si tu base de datos se filtra, no debe revelar las contraseñas reales de nadie.

¿Qué es el hashing?

El hashing convierte la contraseña en una cadena irreversible. De "miClave123" obtienes algo como $2a$10$N9qo8uLOickgx2ZMRZoMy.... Es un proceso de una sola dirección: puedes convertir la contraseña en hash, pero NO puedes recuperar la contraseña desde el hash.

"miClave123"
→ bcrypt convierte (hash) → $2a$10$N9qo8uLOick...
Reverso
✗ NO existe forma de volver del hash a "miClave123". Imposible.

¿Cómo se verifica el login entonces?

Si no podemos recuperar la contraseña, ¿cómo comparamos en el login? Sencillo: hasheamos la contraseña que el usuario escribe al hacer login, y comparamos los dos hashes. bcrypt tiene una función compare que hace exactamente eso.

El "salt": por qué bcrypt es especial

bcrypt añade un valor aleatorio llamado salt a cada contraseña antes de hashearla. Esto significa que dos usuarios con la misma contraseña "123456" tendrán hashes diferentes. Esto bloquea ataques con tablas precalculadas (rainbow tables).

Modificar el modelo User

Primero, añadimos el campo password al esquema, y usamos un "hook" de Mongoose para cifrar automáticamente antes de guardar.

models/User.js
const mongoose = require('mongoose');
const bcrypt = require('bcryptjs');

const userSchema = new mongoose.Schema({
  nombre: {
    type: String,
    required: [true, 'El nombre es requerido'],
    trim: true
  },
  email: {
    type: String,
    required: [true, 'El email es requerido'],
    unique: true,
    lowercase: true,
    match: [/^\w+([\.-]?\w+)*@\w+([\.-]?\w+)*(\.\w{2,3})+$/, 'Email inválido']
  },
  password: {
    type: String,
    required: [true, 'La contraseña es requerida'],
    minlength: [6, 'La contraseña debe tener al menos 6 caracteres'],
    select: false   // ← no se devuelve en las consultas por defecto
  },
  rol: {
    type: String,
    enum: ['usuario', 'admin'],
    default: 'usuario'
  }
}, { timestamps: true });

// HOOK: se ejecuta ANTES de guardar (pre 'save')
userSchema.pre('save', async function (next) {
  // Solo hashear si la contraseña fue modificada
  if (!this.isModified('password')) {
    return next();
  }
  // Generar el salt y hashear
  const salt = await bcrypt.genSalt(10);
  this.password = await bcrypt.hash(this.password, salt);
  next();
});

// MÉTODO: comparar contraseña en el login
userSchema.methods.compararPassword = async function (passwordIngresada) {
  return await bcrypt.compare(passwordIngresada, this.password);
};

module.exports = mongoose.model('User', userSchema);

Desglose de lo nuevo

  • select: false: por defecto, las consultas NO devolverán la contraseña, ni siquiera cifrada. Buena práctica.
  • userSchema.pre('save', ...): un hook que corre justo antes de guardar. Aquí cifrramos automáticamente.
  • if (!this.isModified('password')): solo re-hasheamos si la contraseña cambió. Si no, al actualizar otros campos volveríamos a hashear un hash. Mal.
  • compararPassword: un método que añadimos al modelo para usarlo cómodamente en el login.

💡 La belleza del hook: Como el cifrado vive en el modelo, cualquier lugar donde guardes un usuario cifrará la contraseña automáticamente. No tienes que acordarte de hacerlo manualmente en cada controlador. El modelo se protege solo.

2Registro de usuarios

Construimos el endpoint donde un usuario nuevo crea su cuenta. Recuerda el flujo del diagrama 1: validar email, cifrar contraseña (automático por el hook), guardar.

El controlador de autenticación

Creamos un archivo nuevo para toda la lógica de auth.

controllers/authController.js
const User = require('../models/User');
const jwt = require('jsonwebtoken');

// Función auxiliar: generar un token JWT
const generarToken = (usuario) => {
  return jwt.sign(
    { id: usuario._id, rol: usuario.rol },   // payload
    process.env.JWT_SECRET,                   // clave secreta
    { expiresIn: process.env.JWT_EXPIRES_IN } // expiración
  );
};

// POST /api/auth/register
exports.registrar = async (req, res) => {
  try {
    const { nombre, email, password } = req.body;

    // 1. Validar que vengan los datos
    if (!nombre || !email || !password) {
      return res.status(400).json({
        exitoso: false,
        mensaje: 'Nombre, email y contraseña son requeridos'
      });
    }

    // 2. Verificar si el email ya está registrado
    const usuarioExiste = await User.findOne({ email });
    if (usuarioExiste) {
      return res.status(400).json({
        exitoso: false,
        mensaje: 'Este email ya está registrado'
      });
    }

    // 3. Crear el usuario (el hook cifra la contraseña solo)
    const usuario = await User.create({ nombre, email, password });

    // 4. Generar token para que entre directo sin re-login
    const token = generarToken(usuario);

    // 5. Responder (sin enviar la contraseña)
    res.status(201).json({
      exitoso: true,
      mensaje: 'Usuario registrado exitosamente',
      token,
      usuario: {
        id: usuario._id,
        nombre: usuario.nombre,
        email: usuario.email,
        rol: usuario.rol
      }
    });
  } catch (error) {
    res.status(500).json({
      exitoso: false,
      mensaje: 'Error al registrar usuario',
      error: error.message
    });
  }
};

El controlador de login

Lo añadimos al mismo authController.js:

controllers/authController.js (añadir)
// POST /api/auth/login
exports.login = async (req, res) => {
  try {
    const { email, password } = req.body;

    // 1. Validar datos
    if (!email || !password) {
      return res.status(400).json({
        exitoso: false,
        mensaje: 'Email y contraseña son requeridos'
      });
    }

    // 2. Buscar el usuario INCLUYENDO el password
    //    (recuerda que pusimos select: false en el modelo)
    const usuario = await User.findOne({ email }).select('+password');

    // 3. Si no existe, error genérico (no revelar qué falló)
    if (!usuario) {
      return res.status(401).json({
        exitoso: false,
        mensaje: 'Credenciales inválidas'
      });
    }

    // 4. Comparar la contraseña con el método del modelo
    const passwordCorrecta = await usuario.compararPassword(password);
    if (!passwordCorrecta) {
      return res.status(401).json({
        exitoso: false,
        mensaje: 'Credenciales inválidas'
      });
    }

    // 5. Todo bien: generar token
    const token = generarToken(usuario);

    // 6. Responder con el token
    res.status(200).json({
      exitoso: true,
      mensaje: 'Login exitoso',
      token,
      usuario: {
        id: usuario._id,
        nombre: usuario.nombre,
        email: usuario.email,
        rol: usuario.rol
      }
    });
  } catch (error) {
    res.status(500).json({
      exitoso: false,
      mensaje: 'Error al iniciar sesión',
      error: error.message
    });
  }
};

Módulo 13 · Implementación

4Middleware de protección

Este es el "portero" del hotel. Una función que se ejecuta ANTES de las rutas protegidas, verifica el token, y solo deja pasar si es válido. Es la pieza central de todo.

¿Qué es un middleware en Express?

Un middleware es una función que recibe (req, res, next) y se ejecuta en medio del camino entre la petición y el controlador. Puede:

  • Inspeccionar o modificar la petición (req).
  • Cortar el flujo respondiendo directamente (res).
  • O dejar pasar al siguiente paso llamando a next().

El middleware de autenticación

middleware/auth.js
const jwt = require('jsonwebtoken');
const User = require('../models/User');

// Middleware: proteger rutas (verifica el token)
exports.proteger = async (req, res, next) => {
  try {
    let token;

    // 1. Buscar el token en el header Authorization
    if (
      req.headers.authorization &&
      req.headers.authorization.startsWith('Bearer')
    ) {
      // El header viene como: "Bearer eyJhbGc..."
      token = req.headers.authorization.split(' ')[1];
    }

    // 2. Si no hay token, denegar acceso
    if (!token) {
      return res.status(401).json({
        exitoso: false,
        mensaje: 'No autorizado, no hay token'
      });
    }

    // 3. Verificar el token (lanza error si firma inválida o expiró)
    const decodificado = jwt.verify(token, process.env.JWT_SECRET);

    // 4. Buscar el usuario y adjuntarlo a la petición
    const usuario = await User.findById(decodificado.id);
    if (!usuario) {
      return res.status(401).json({
        exitoso: false,
        mensaje: 'El usuario de este token ya no existe'
      });
    }

    // 5. Guardar el usuario en req para los siguientes pasos
    req.usuario = usuario;

    // 6. Dejar pasar al controlador
    next();
  } catch (error) {
    return res.status(401).json({
      exitoso: false,
      mensaje: 'Token inválido o expirado'
    });
  }
};

Desglose paso a paso

PasoQué hace
1Lee el header Authorization y extrae el token de "Bearer <token>".
2Si no hay token → 401 y se acaba aquí. No llega al controlador.
3jwt.verify revisa la firma y la expiración. Si algo está mal, lanza error y caemos al catch.
4Con el id del payload, busca el usuario real en la base de datos.
5Pone el usuario en req.usuario para que el controlador sepa quién es.
6next() = "puedes pasar". Cede el control al controlador.

Bonus: middleware de autorización por rol

Recuerda Authn vs Authz. Ya verificamos quién eres. Ahora un middleware extra para qué puedes hacer:

middleware/auth.js (añadir)
// Middleware: autorizar solo ciertos roles
exports.autorizar = (...rolesPermitidos) => {
  return (req, res, next) => {
    // req.usuario ya existe porque 'proteger' corrió antes
    if (!rolesPermitidos.includes(req.usuario.rol)) {
      return res.status(403).json({
        exitoso: false,
        mensaje: `El rol '${req.usuario.rol}' no tiene permiso para esta acción`
      });
    }
    next();
  };
};

Fíjate que esto es una función que devuelve otra función. Eso permite usarla así: autorizar('admin'). Lo veremos en acción en la siguiente sección.

📌 Diferencia clave de códigos: 401 Unauthorized = "no sé quién eres" (falló authn). 403 Forbidden = "sé quién eres, pero no puedes hacer esto" (falló authz). Usar el código correcto es buena práctica profesional.

Módulo 14 · Implementación

5Proteger rutas

Ya tenemos el portero. Ahora lo ponemos a trabajar: aplicamos el middleware a las rutas que queremos proteger. Aquí todo cobra sentido.

Cómo se aplica un middleware a una ruta

En Express, pones el middleware ANTES del controlador en la definición de la ruta. Express los ejecuta en orden.

routes/userRoutes.js
const express = require('express');
const router = express.Router();
const {
  obtenerUsuarios,
  obtenerUsuarioPorId,
  eliminarUsuario
} = require('../controllers/userController');
const { proteger, autorizar } = require('../middleware/auth');

// PÚBLICA: cualquiera puede ver (si así lo decides)
router.get('/', obtenerUsuarios);

// PROTEGIDA: requiere token válido
router.get('/:id', proteger, obtenerUsuarioPorId);

// PROTEGIDA + SOLO ADMIN: requiere token Y rol admin
router.delete('/:id', proteger, autorizar('admin'), eliminarUsuario);

module.exports = router;

Lee la cadena de izquierda a derecha

En router.delete('/:id', proteger, autorizar('admin'), eliminarUsuario):

  1. Llega la petición DELETE.
  2. proteger corre: ¿token válido? Si no → 401, fin.
  3. autorizar('admin') corre: ¿es admin? Si no → 403, fin.
  4. Solo si ambos pasan, corre eliminarUsuario.

Módulo 16 · Cierre

Otras opciones y hacia dónde seguir

Ya dominas la base. Estas son las extensiones naturales que verás cuando trabajes en proyectos más grandes. No para implementar hoy, sino para que sepas que existen.

Refresh Tokens

El problema: un token de larga duración robado da acceso por mucho tiempo. La solución de dos tokens:

TokenDuraciónPara qué
Access tokenCorto (15 min)Acceder a rutas. Si lo roban, expira rápido.
Refresh tokenLargo (7 días)Pedir nuevos access tokens sin re-login.

Cuando el access token expira, el cliente usa el refresh token para obtener uno nuevo, todo en segundo plano. El usuario ni se entera.

Logout con JWT

Aquí hay un detalle interesante: como JWT es stateless, el servidor no puede "invalidar" un token. Soluciones comunes:

  • Tokens cortos: si expira pronto, el logout es casi instantáneo de facto.
  • Blocklist: guardar tokens "cerrados" en Redis hasta que expiren. (Esto reintroduce algo de estado.)
  • Borrar el token del cliente: en muchos casos, simplemente borrar el token del frontend es suficiente.

OAuth 2.0 / "Login con Google"

Delegas la autenticación a un proveedor. El flujo simplificado:

Usuario
1. Click en "Iniciar sesión con Google".
Google
2. Google pide login y permiso. El usuario acepta.
Google
3. Google le confirma a tu API quién es el usuario.
Tu API
4. Creas/buscas el usuario y emites tu propio JWT.

Ventaja: no manejas contraseñas, el usuario confía en Google. En Node, librerías como Passport.js facilitan esto enormemente.

Librerías que te ahorran trabajo

Passport.js

El estándar en Node para estrategias de autenticación (local, Google, GitHub, etc.).

express-validator

Validación robusta de los datos de entrada antes de procesarlos.

helmet

Añade headers de seguridad HTTP automáticamente. Una línea, mucha protección.

express-rate-limit

Limita intentos por IP. Esencial contra fuerza bruta en el login.

Módulo 17 · Cierre

Seguridad y buenas prácticas

La autenticación es donde un error se paga caro. Esta es la lista de comprobación que todo backend debe respetar. Imprímela y pégala en la pared.

Las reglas de oro

ReglaPor qué
NUNCA guardes contraseñas en texto planoSi filtran la BD, todas las cuentas caen. Siempre hashea con bcrypt.
NUNCA pongas datos sensibles en el payload del JWTEl payload es legible por cualquiera. Solo id, rol, datos no sensibles.
SIEMPRE usa HTTPS en producciónSin HTTPS, el token viaja en texto plano y puede ser interceptado.
SIEMPRE pon expiración a los tokensUn token eterno robado es acceso eterno. Usa expiresIn.
La JWT_SECRET debe ser larga y aleatoriaUna clave débil se puede adivinar y permite falsificar tokens.
NUNCA subas el .env a GitFiltrarías tu clave secreta. Añádelo a .gitignore siempre.
Mensajes de error genéricos en login"Credenciales inválidas" no revela si el email existe.
Verifica SIEMPRE en el backendEl frontend se puede manipular. La seguridad real vive en el servidor.
Valida y limpia toda entrada del usuarioPreviene inyecciones y datos corruptos.
Limita los intentos de login (rate limiting)Frena ataques de fuerza bruta.

Errores comunes de principiantes

❌ Error 1: Hashear la contraseña en el frontend. NO. El hashing va en el backend. Si lo haces en el front, el hash se convierte en "la contraseña real" y pierdes toda la protección.

❌ Error 2: Devolver la contraseña (aunque sea cifrada) en las respuestas de la API. Usa select: false y nunca la incluyas en el JSON de respuesta.

❌ Error 3: Confiar en que el frontend ocultó un botón. Un atacante llama tu API directo con Postman. La verificación SIEMPRE en el backend.

❌ Error 4: Poner la JWT_SECRET directamente en el código ("miclave123"). Siempre en variables de entorno, nunca hardcodeada.

Checklist final del proyecto

Tu API tiene autenticación bien hecha si:

☑ Las contraseñas se guardan cifradas con bcrypt
☑ El login devuelve un JWT con expiración
☑ Las rutas privadas están protegidas con middleware
☑ Los roles controlan acciones sensibles (autorización)
☑ La JWT_SECRET está en .env y .env está en .gitignore
☑ Los errores de login son genéricos
☑ Probaste cada ruta con y sin token
☑ Ningún endpoint devuelve la contraseña
